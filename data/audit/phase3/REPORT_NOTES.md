# 环肽专利印刷 SMILES 识别 — 汇报要点

日期：2026-10-28
配套材料：`PHASE3_SUMMARY.md`（完整证据链）、`figure_route/figure_1036_route.png`（证据图）

---

## 一句话结论

**生产 OCR 读不懂专利印刷 SMILES 有两个叠加原因，都已定位到可复现的证据上：
① 识别器模型选错了——生产用的英文 PP-OCRv4 在读 `C(=O)` 时会漏掉左括号，
这解释了正式 CSV 里 335/335 条括号失衡；② 单元格裁剪本身有两处几何缺陷
（贯穿全高的竖直表格线、垂直 padding 只有 4/5 px）。**

**两处都修掉之后，用同一套配置在 I100298 的 21 个印刷行上达到逐字符完全一致，
其中 1038 是留出集（未参与配置选择）。**

## 可以讲的四件事

### 1. 把一个从未被验证过的重大缺陷量化了出来

- 正式 CSV 里 335 条印刷 SMILES，**括号全部失衡，RDKit 全部无法解析（0/335）**。
- 独立重跑生产流程与已发布 CSV 的括号失衡量相关系数 **0.9861**，228/335 条字符完全一致
  → 缺陷来自流水线本身，不是某一次偶发运行。
- 这一层以前没有任何独立核验，汇报时属于"新发现"。

### 2. 纠正了一个一直没人质疑的前提：所谓"基线"在生产里并不存在

- 生产通路是 `cell → trim → 2× 放大 → 识别`，**全程没有二值化**。
- 而 Phase 2 用来衡量所有优化方向的"基线"（`binarize_up2_en`），**生产环境从来没有用过**。
- 因此此前"加阈值无效""padding 无效""扩框无效"等一串结论，实际上都是在和
  一个流水线里不存在的配置做比较。这条纠正比任何单项优化都重要。

### 3. 用受控实验把根因定位到识别器模型

同一批检测框、同一张裁剪图，**只换识别器**：

| 识别器 | 1036 编辑距离 | 1036 括号 开/闭 | 全量 335 括号配平 |
|---|---|---|---|
| 生产：`en_PP-OCRv4_rec_mobile` | 82 | 18 / 33 | **0/335** |
| 默认：`PP-OCRv6_rec_small`（中文） | **0** | **38 / 38** | **190/335** |

识别器是唯一变量，所以结论是确定的：英文识别器在 `C(=O)` 上输出 `C=O`，
左括号直接丢失——这就是 335/335 失衡的原因。

### 4. 修复方案在三个人工核对参考上做到逐字符一致

| cmpd | 生产 | 生产+阈值200 | 整页识别 | **整页检测+逐行裁剪** |
|---|---|---|---|---|
| 1036（用户手抄，人工核对） | 82 | 9 | 31 | **0 / CER 0** |
| 1037（本轮独立复核，人工核对） | 89 | 6 | 0 | **0 / CER 0** |
| 1038（研究者提供，人工核对） | — | — | — | **0 / CER 0** |

1037 的参考本轮升级为"已人工逐字核对"：早前的转录与本次从原图逐行重读**逐字符一致**，
初次出现的差异经复核是裁切边界压掉了行首字形（已记录在 `reference_status.md`）。

### 5. 新结果：I100298 的单元格几何修正（最新，2026-10-28）

这是目前最有价值的一条，也是"这几天做了什么"的答案。

**发现了两个此前从未测过的几何缺陷**

1. 单元格裁剪里含有**贯穿全高的竖直表格线**（1040 单元格在 x=0–1 与
   x=840–841），它会原样进入 OCR 输入；
2. 印刷行的**垂直 padding 只有 4/5 px**，字形上下被相邻行挤住。

**修正方式（单一配置，所有行、所有化合物通用，不逐行拟合）**

```
trim 竖直表格线 → 2× INTER_CUBIC → 不做二值化 → 墨迹带上下各 14/15 px padding
识别器：上游默认引擎（PP-OCRv6 det + PP-OCRv6 rec）
```

**结果**

| cmpd | 参考状态 | 编辑距离 | CER | 括号 | RDKit | 确定性 |
|---|---|---|---|---|---|---|
| 1038 | 研究者提供，**留出集** | **0** | 0.0 | 40/40 | 通过 | 是 |
| 1039 | 印刷转录，待人工核 | **0** | 0.0 | 39/39 | 通过 | 是 |
| 1040 | 印刷转录，待人工核 | **0** | 0.0 | 38/38 | 通过 | 是 |
| 1041 | 印刷转录，待人工核 | **0** | 0.0 | 38/38 | 通过 | 是 |

21 个印刷行逐行编辑距离全部为 0。正式 CSV 的 SHA256 全程未变。

**为什么值得单独讲**：这是**单元格路线第一次做到逐字符正确**。
此前 `cell/default/up2` 在 1036 上还有 166 个错误；而整页检测路线虽然准，
却在 335 条里漏掉 28 行、且对左边界 margin 极度敏感（0/8/16/24 px 互相矛盾）。
把单元格自己的两个几何缺陷修掉，就不必依赖那条更脆弱的整页路线。

## 必须主动讲清的三点（否则会被追问）

1. **人工逐字核对的参考共 3 个**（1036、1037、1038）；1039–1041 的参考是
   agent 转录、**明天上午核对后才能升级**。I100298 只是一页 4 个化合物 / 21 行，
   不能外推为全量准确率。
2. **"括号配平"和"RDKit 可解析"都不能当准确率用**。实测证明这些代理指标
   与逐字符正确性会互相矛盾：例如某配置括号配平 169/335 但 1036 错 166 个字符，
   另一配置配平仅 54/335 但 1036 只错 9 个字符。全量数字一律按"文本层面的代理指标"表述。
3. **结构级正确性（L4）目前没有任何一条通过验证**。质量门通过 ≠ 结构正确，
   本阶段全部结论停留在文本层面（L1–L3）。

## 另一个必须如实说明的脆弱性

识别结果对裁剪几何**高度敏感**：同一个 1036、同一批检测框，左边界差 3 px，
编辑距离在 **0** 和 **31** 之间跳变；左边界外扩 24 px 能让 1036 回到 0，
却让 1037 从 0 变成 34。

→ 说明任何"单样本调出来的最优参数"都不足以作为生产依据。

**这一点已经用全量扫描证实（335 单元格 / 80 页 / 0 错误）**：
左边界外扩 0 / 8 / 16 / 24 px 对应的括号配平是 180 / **190** / 180 / 146，
而 1036 的编辑距离是 31 / 57 / 37 / **0**，1037 是 0 / 0 / 0 / 34。
**语料最优（8 px）与参考最优（24 px）互相矛盾 → 扩大裁剪框不是解法，这个方向可以关闭。**
几何原因也查清了：335 行裁剪框的左边界全部位于 SMILES 列边界左侧，
任何外扩都会把结构列墨迹拉进裁剪框。

**补充（2026-10-28）**：上述脆弱性属于**整页检测 + 逐行裁剪**那条路线。
最新的 I100298 单元格几何修正走的是另一条路——在单元格裁剪内部修掉
竖直表格线与垂直 padding，不做任何边界外扩，因此不受左边界 margin 影响。
该路线尚未在全量 335 条上验证，这是下一步的首要任务。
